## 0. 概念先行：有了 02 章的 CI/CD，为什么还要 GitOps

02 章的 GitLab CI 是**"推式"发布**：你 git push → CI 跑构建 → CI 主动执行 kubectl 把应用"推"上集群。它有一个隐患：**发布动作由 CI 临时机器发起，集群里实际跑着什么，只有 CI 知道**。谁在集群里手动改过、什么时候改的，Git 里查不到。

**GitOps（ArgoCD）是"拉式"**：ArgoCD 常驻集群，一直盯着 Git 仓库，发现"Git 里写的"和"集群里跑的"不一致就主动纠正（自动 sync）。好处：

1. **Git 是唯一事实源**——发版 = 改 Git；回滚 = git revert
2. **防漂移**——谁在集群里手动改了什么，ArgoCD 会把它拉回 Git 定义的状态
3. **审计**——git log 就是完整的发布历史

本章三件事的定位：

| 组件 | 回答的问题 | 类比 |
|---|---|---|
| ArgoCD | 应用怎么发布、怎么保证集群和 Git 一致 | 自动对账的发版管家 |
| Velero | 集群坏了/误删了，怎么恢复 | 集群级"整机备份+还原" |
| Alertmanager | 出问题时，怎么让**人**知道 | 值班电话（铃响了才会有人来处理） |

## 1. ArgoCD —— GitOps 发版

### 1.1 安装

```bash
# 1.1.1 官方清单安装（所有组件都在 argocd 命名空间）
kubectl create namespace argocd
kubectl apply -n argocd -f https://raw.githubusercontent.com/argoproj/argo-cd/stable/manifests/install.yaml

# 1.1.2 等就绪
kubectl -n argocd get pods -w

# 1.1.3 取初始 admin 密码（账号 admin）
kubectl -n argocd get secret argocd-initial-admin-secret \
  -o jsonpath="{.data.password}" | base64 -d && echo

# 1.1.4 访问 UI（教学用端口转发；想配正式域名+HTTPS，用 05 章学过的 MetalLB + cert-manager 组合）
kubectl -n argocd port-forward svc/argocd-server 8080:443
# 浏览器 https://localhost:8080，账号 admin
```

> 登录后建议先改密码（界面 User Info → Update Password），生产还会接公司的 SSO。

### 1.2 创建 Application：让 ArgoCD 接管 k8s-demo

概念：**Application** 是 ArgoCD 的核心对象，一句话定义"从哪个 Git 仓库的哪个目录、装到哪个集群的哪个命名空间"。k8s-demo 仓库里已经有完整的 Helm chart（`k8s/helm/k8s-demo`），直接指向它：

```yaml
# 1.2.1 把下面内容存成 /tmp/k8s-demo-app.yaml 再 apply
#  values 内嵌在 Application 里（正式用法也可以建单独的 values 文件放仓库里）
#  repoURL 换成你自己的仓库（GitHub 或 02 章自建的 GitLab 都行）
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: k8s-demo
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/Marsvvv/k8s-demo.git
    targetRevision: main
    path: k8s/helm/k8s-demo
    helm:
      values: |
        image:
          registry: core.harbor.<服务器IP>.sslip.io:8443/k8s-demo
        mysql:
          storageClass: nfs-client
        rabbitmq:
          storageClass: nfs-client
        efk:
          esStorageClass: nfs-client
  destination:
    server: https://kubernetes.default.svc
    namespace: k8s-demo
  syncPolicy:
    automated:
      prune: true      # Git 里删了的资源，集群里也删
      selfHeal: true   # 集群被手动改过，自动拉回 Git 定义（防漂移的关键开关）
EOF
```

```bash
kubectl apply -f /tmp/k8s-demo-app.yaml

# 1.2.2 UI 里看同步状态：Application → k8s-demo → 状态变 Synced/Healthy
#   含义解读：Synced = 集群现状和 Git 一致；Healthy = 应用健康检查通过
#   如第一次同步因为镜像/存储类配置不对而失败，改 values 重试即可（这正是 GitOps 的调试方式）
```

> 注意：ArgoCD 会接管 `k8s-demo` 命名空间里的同名资源。如果之前 05 章用 helm 部署过一套，先 `helm uninstall k8s-demo -n k8s-demo` 避免两边打架。

### 1.3 两个必做实验（GitOps 精髓就在这）

**实验一：git push 发版。** 改仓库里的 chart 值（比如 `k8s/helm/k8s-demo/values.yaml` 把 userService.replicas 改成 4），push 后 ArgoCD 每 3 分钟自动发现差异并 sync（或界面点 Refresh + Sync 立即执行）。**发版 = 改 Git + push，没有第二条路。**

**实验二：防漂移。** 故意绕开 Git 手动改集群：

```bash
kubectl -n k8s-demo scale deployment/user-service --replicas=1
# 等几秒再看：ArgoCD 检测到"集群 1 个副本 ≠ Git 里 2 个"，自动拉回 2 个
kubectl -n k8s-demo get deploy user-service
```

> 输出解读：副本数自己弹回 2——这就是 selfHeal。生产意义：**任何人偷偷在生产上手动改的配置都会被 Git 状态纠正**，改配置必须走 PR 流程，这就是 GitOps 带来的治理能力。

## 2. Velero —— 集群级备份与恢复

### 2.1 概念：备份到底备份什么（三层）

集群的数据分三层，出事后的恢复诉求也分三层：

| 层 | 内容 | 例子 | 用什么备份 |
|---|---|---|---|
| 状态层 | 集群的"配置记录" | 有哪些 Deployment/Service/ConfigMap | etcd 快照 / Velero 的资源备份 |
| 对象层 | 部署清单级 | 一个 namespace 的整套应用 | Velero（本层+上层一起） |
| 数据层 | 业务数据 | MySQL 的数据盘（PVC） | Velero 的卷快照/文件级备份 |

**Velero 是标准工具**：备份"资源对象 + PVC 数据"到 S3 兼容存储，支持按 namespace/标签筛选，恢复时重建整套应用。生产还有定时备份（schedule）。

### 2.2 准备 MinIO（S3 兼容存储，放备份文件）

```bash
# 2.2.1 真机上用 docker 起 MinIO（备份文件就存在它的数据目录里）
mkdir -p ~/minio-data
docker run -d --name minio -p 9000:9000 -p 9001:9001 \
  -v ~/minio-data:/data \
  -e MINIO_ROOT_USER=minioadmin -e MINIO_ROOT_PASSWORD=k8s123456 \
  minio/minio server /data --console-address ":9001"

# 2.2.2 建桶：浏览器开 http://<服务器IP>:9001（MinIO 控制台），登录后
#   Buckets → Create Bucket → 名称 velero → 创建
```

### 2.3 安装 Velero 并指向 MinIO

```bash
# 2.3.1 装 CLI（node1 上）
wget https://github.com/vmware-tanzu/velero/releases/download/v1.13.2/velero-v1.13.2-linux-amd64.tar.gz
tar xzf velero-v1.13.2-linux-amd64.tar.gz && sudo mv velero-v1.13.2-linux-amd64/velero /usr/local/bin/

# 2.3.2 写 MinIO 凭据文件
cat > ~/credentials-velero <<'EOF'
[default]
aws_access_key_id = minioadmin
aws_secret_access_key = k8s123456
EOF

# 2.3.3 安装 Velero 服务端（--use-node-agent 让每个节点有个代理负责"文件级"备份 PVC 数据；
#       s3Url 指向我们的 MinIO；use-volume-snapshots 关掉——那是云厂商快照用的，裸金属没有）
velero install \
  --provider aws \
  --plugins velero/velero-plugin-for-aws:v1.9.2 \
  --bucket velero \
  --secret-file ~/credentials-velero \
  --backup-location-config region=minio,s3ForcePathStyle=true,s3Url=http://<服务器IP>:9000 \
  --use-volume-snapshots=false \
  --use-node-agent \
  --default-volumes-to-fs-backup

# 2.3.4 等就绪
kubectl -n velero get pods -w   # velero 和 node-agent 都 Running
```

### 2.4 备份 → 亲手"弄坏" → 恢复（本章第二个高潮实验）

```bash
# 2.4.1 备份整个 k8s-demo 命名空间（PVC 数据由 node-agent 文件级备份带走）
velero backup create k8s-demo-bak --include-namespaces k8s-demo
velero backup get k8s-demo-bak
# 输出解读：STATUS 变 Completed = 资源对象已备份；看 PHASE 等待完成

# 2.4.2 "事故"：整个命名空间删掉（模拟误删/被黑）
kubectl delete namespace k8s-demo
kubectl get pods -n k8s-demo   # 报 not found —— 应用没了

# 2.4.3 恢复：一条命令全部重建（应用、配置、PVC 数据一起回来）
velero restore create --from-backup k8s-demo-bak
kubectl -n k8s-demo get pods -w   # 全套重新拉起，PVC 重新挂上

# 2.4.4 验证数据真的回来了：浏览器下单链路照常，且之前的订单/用户数据还在（读 Redis/MySQL）
```

> **输出解读**：恢复后能看到 PV/PVC 被重新创建、Pod 重新调度——Velero 记录的不仅是"有哪些资源"，还有它们之间的关联关系，所以能整套还原。这就是它和"手工 etcd 快照"的区别：etcd 快照只能整集群回滚，Velero 可以按命名空间/标签**选择性**备份和恢复。
>
> 生产习惯：把 2.4.1 换成定时任务 `velero schedule create daily-bak --schedule="0 2 * * *" --include-namespaces k8s-demo`，每天凌晨自动备份。

## 3. Alertmanager —— 出问题时通知人

### 3.1 概念：监控 ≠ 告警

03 章装过 Prometheus + Grafana：那套负责**看见**问题（图表上 CPU 红了）。但没有人 24 小时盯着 Grafana。**告警负责"叫人"**：规则触发 → Alertmanager 收到 → 按路由发给钉钉/邮件/短信 → 有人来处理。

链路：`Prometheus 指标 → PrometheusRule（什么算异常）→ Alertmanager（发给谁、怎么发）→ 钉钉/邮件`。

### 3.2 配一条告警规则

03 章的 kube-prometheus-stack 已自带 Alertmanager，直接加规则：

```bash
# 3.2.1 告警规则：Pod 频繁重启（15 分钟内重启 5 次以上 → 触发）
kubectl apply -f - <<'EOF'
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: demo-alert-rules
  namespace: monitoring
spec:
  groups:
    - name: demo
      rules:
        - alert: PodCrashLooping
          expr: rate(kube_pod_container_status_restarts_total{namespace="k8s-demo"}[15m]) > 0.05
          for: 1m
          labels:
            severity: critical
          annotations:
            summary: "Pod {{ $labels.pod }} 频繁重启"
            description: "15 分钟内重启 {{ $value }} 次，去 kubectl logs 看看"
EOF

# 3.2.2 触发演练：故意造一个"起不来的 Pod"（镜像名写错 → CrashLoopBackOff）
kubectl -n k8s-demo run crash-demo --image=nginx:不存在 --restart=Always
# 等 1~2 分钟……

# 3.2.3 看告警状态：浏览器（先端口转发）
kubectl -n monitoring port-forward svc/kube-prometheus-stack-alertmanager 9093:9093
# 浏览器 http://localhost:9093 → Alerts 页：PodCrashLooping 状态 pending → firing（已触发）
```

> 输出解读：`pending` = 条件满足了但在等 `for: 1m` 的持续时长（防止瞬时抖动误报）；`firing` = 持续超标，正式触发、开始通知。演练完删掉 crash-demo：`kubectl -n k8s-demo delete pod crash-demo`，告警自动恢复。

### 3.3 把告警送到钉钉（国内最常用）

```bash
# 3.3.1 先在钉钉建机器人拿 webhook 地址（钉钉群 → 群设置 → 机器人 → 自定义 → 复制 webhook）
#   然后创建"通知接收者 + 路由"（AlertmanagerConfig）：
kubectl apply -f - <<'EOF'
apiVersion: monitoring.coreos.com/v1alpha1
kind: AlertmanagerConfig
metadata:
  name: dingtalk-config
  namespace: monitoring
spec:
  route:
    groupBy: ["alertname"]
    receiver: dingtalk
    groupInterval: 1m
    repeatInterval: 4h      # 同一个告警多久重发一次，防止刷屏
  receivers:
    - name: dingtalk
      webhookConfigs:
        - url: https://oapi.dingtalk.com/robot/send?access_token=<你的token>
          sendResolved: true   # 恢复时也通知（"故障已解决"）
EOF
# 3.3.2 再触发一次演练（重复 3.2.2），钉钉群应收到告警消息
```

> 生产注意：告警规则要少而精（每条都对应"需要人行动"的场景），否则告警疲劳后没人看；severity 分级（critical 打负责人电话、warning 发群）也是标配。邮件通知方式同理，把 webhookConfigs 换成 emailConfigs 即可。

## 4. 生产检查清单（自建集群交付前逐项过一遍）

| 维度 | 检查项 | 对应章节 |
|---|---|---|
| 发版 | 应用由 ArgoCD/GitOps 管理，改集群配置必须走 Git | 07 §1 |
| 备份 | 定时备份已建、最近一次恢复演练成功 | 07 §2 |
| 告警 | 告警规则触发后钉钉/邮件真的能收到 | 07 §3 |
| 入口 | 应用有域名 + HTTPS（无自签警告） | 05 §1/§4 |
| 仓库 | 镜像只从 Harbor 拉取，仓库有账号权限 | 05 §3 |
| 存储 | 有状态应用的数据在共享存储上 | 05 §2 |
| 高可用 | 控制面 ≥3、应用 ≥2 副本、故障演练做过 | 06 |
| 监控 | Grafana 面板有人看、指标保留期够用 | 03 §6 |
| 日志 | EFK 可检索，日志保留策略明确 | 01/03 §7 |
| 资源 | Pod 有 requests/limits，节点资源余量 ≥30% | 01 手册 |
| 安全 | 密码进 Secret、RBAC 最小权限、镜像扫描开启 | 03 §3 |

> 这张清单就是"自建集群能交出去"的及格线。全部勾上后，你这套环境已经是完整生产形态的缩小版。

## 常见坑速查

| 现象 | 原因/解决 |
|---|---|
| ArgoCD UI 打不开 | port-forward 的 8080 被占；换 `8080:443` 的端口号，或配正式 ingress |
| Application 一直 OutOfSync | Git 里的配置和集群不一致且 sync 失败：UI 看 Sync 报错（多半是镜像拉不到/存储类不存在），改 values 或修集群 |
| ArgoCD 的 git 仓库连不上 | 自建 GitLab 用自签证书：Application 里配 `insecureIgnoreHostKey`，或给 argocd 加仓库 CA（UI → Settings → Repositories） |
| velero install 报 S3 连不上 | MinIO 没起/桶没建/端口写错；`curl http://<服务器IP>:9000` 先验证 MinIO 活着 |
| 备份成功但恢复后 PVC 没数据 | 没开 `--default-volumes-to-fs-backup`，或应用没挂 PVC（文件级备份只对 PVC 生效） |
| 恢复后 Pod 起不来 | 恢复顺序问题：先等 PVC/Secret 恢复完成再看 Pod；`velero restore describe` 看明细 |
| 钉钉收不到告警 | webhook 地址带 access_token 才算有效；AlertmanagerConfig 的 route 没匹配上（namespace/label 选择器） |
| 告警一直 pending 不 firing | 正常：`for: 1m` 要求持续超标才触发，等够时长 |
