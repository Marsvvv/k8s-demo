## 0. 本章地图：四个组件各解决一个"真实环境才会有的问题"

| 04 章埋的坑 | 本章解法 | 它到底在解决什么 |
|---|---|---|
| LoadBalancer 永远 Pending | **MetalLB** | 裸金属没有云负载均衡器，需要自己造一个 |
| RKE2 集群没有默认存储类，PVC 卡 Pending | **NFS provisioner** | 真实集群要共享存储，Pod 换节点数据不丢 |
| 只有裸 registry（无账号、无界面、无扫描） | **Harbor** | 正式镜像仓库：账号体系、项目隔离、镜像扫描 |
| 全是自签证书、浏览器告警 | **cert-manager** | 证书自动签发、自动续期 |

```
你的浏览器 ── https（证书由 cert-manager 自动签发）──► MetalLB 分配的 IP
                                                        │
                    ┌───────────────────────────────────┤
                    │ 真机自建集群（RKE2）               │
                    │  ├─ 应用 Pod（k8s-demo 全套）      │
                    │  │     │ 拉镜像                    │
                    │  │     ▼                          │
                    │  ├─ Harbor（镜像仓库，docker 独立部署）│
                    │  └─ PVC ──► NFS 共享存储          │
                    └───────────────────────────────────┘
```

## 1. MetalLB —— 给裸金属装上"云负载均衡器"

### 1.1 概念：LoadBalancer 类型的 Service 到底在等谁

K8s 里 Service 有四种暴露方式：ClusterIP（集群内）、NodePort（每台机器开端口）、LoadBalancer（**云厂商给我分配一个公网入口 IP**）、ExternalName（转发到外部域名）。

04 章那个 Pending 之谜的本质：`type: LoadBalancer` 这句话是对**云环境**说的——"请云厂商的负载均衡器给我分配一个 IP"。云上有对应组件响应它（阿里云 SLB、AWS ELB）；**裸金属上没有，所以永远没人应答**。

### 1.2 概念：MetalLB 怎么工作（L2 模式）

MetalLB 就是一个"山寨云负载均衡器"，它监听集群里的 LoadBalancer 请求，从你指定的地址池里分配一个**局域网 IP** 给它。默认 L2 模式的工作原理一句话：**MetalLB 替那个 IP 在局域网里做 ARP 广播——"这个 IP 在我这"**，于是局域网里的流量就被引到这台机器上。

> 生产说明：L2 模式够单机和中小集群用；大规模生产用 BGP 模式（和路由器通信，全网络可达）。本章只讲 L2。

### 1.3 安装 + 配置地址池

```bash
# 1.3.1 安装（MetalLB 官方清单）
kubectl apply -f https://raw.githubusercontent.com/metallb/metallb/v0.14.3/config/manifests/metallb-native.yaml

# 1.3.2 等它的控制器就绪
kubectl -n metallb-system get pods -w   # controller 和 speaker 都 Running

# 1.3.3 建地址池 + L2 宣告：把下面内容存成 /tmp/metallb-pool.yaml 再 apply
#   addresses 换成你局域网的空闲地址段（先 ping 一下确认没人用）
#   云主机注意：云上买的是"弹性 IP"，和云内网 IP 不是一回事，L2 模式在云上不生效
#   （云上直接用云厂商的 LoadBalancer，MetalLB 是给物理机/内网用的）
cat > /tmp/metallb-pool.yaml <<'EOF'
apiVersion: metallb.io/v1beta1
kind: IPAddressPool
metadata:
  name: first-pool
  namespace: metallb-system
spec:
  addresses:
    - 192.168.1.200-192.168.1.220
---
apiVersion: metallb.io/v1beta1
kind: L2Advertisement
metadata:
  name: l2
  namespace: metallb-system
EOF
kubectl apply -f /tmp/metallb-pool.yaml
```

### 1.4 验证：把 04 章的 NodePort 补丁正式"转正"

```bash
# 1.4.1 把 Rancher 入口服务改回 LoadBalancer 类型（04 章补丁的反操作）
kubectl -n cattle-system patch svc rancher-ingress-controller -p '{"spec":{"type":"LoadBalancer"}}'

# 1.4.2 这次 EXTERNAL-IP 不再是 <pending>，而是 MetalLB 分配的局域网 IP
kubectl -n cattle-system get svc rancher-ingress-controller
# 输出解读：EXTERNAL-IP 出现 192.168.1.200 —— 这就是 MetalLB 干活的证据
```

浏览器直接访问 `https://rancher.<服务器IP>.sslip.io`（**不再需要 3xxxx 端口了**，标准 443）。为什么能通：sslip.io 把域名解析到 LB IP 192.168.1.200 → MetalLB 在局域网宣告这个 IP → 流量进 nginx-ingress → Rancher。

> 顺带的好处：以后所有服务都走 LoadBalancer + 域名，再也不用记 NodePort 端口号了。生产上这就是"入口统一"的第一步。

## 2. NFS provisioner —— 共享存储

### 2.1 概念：PVC 为什么卡住了（kind 与 RKE2 的真实差异）

PVC（PersistentVolumeClaim）是"我要 5G 存储"的申请单，而 **StorageClass** 是"谁来接单"——它绑定的 provisioner 负责真正创建存储。kind 自带 local-path provisioner，所以 01 章 PVC 直接成功；**RKE2 默认什么都没有**，你申请 PVC 就会永远 Pending。

更根本的问题：local-path 的存储长在"某一台机器的本地磁盘"上。Pod 今天在 A 机器、明天漂到 B 机器，数据就"留在老家"了。真实集群需要**共享存储**——数据放在大家都能访问的地方。

### 2.2 概念：NFS 是什么

NFS（Network File System）是 Linux 世界的"网络共享文件夹"：一台机器导出目录，其他机器挂载访问，读写走网络。用它做 K8s 存储的意思是：**所有节点的 Pod 挂的都是同一块盘**，漂到哪数据都在。缺点是性能一般（走网络），所以适合放配置文件、一般数据；数据库这种高 IO 场景生产会用更好的方案，教学用 NFS 足够。

### 2.3 安装（NFS 服务端 + provisioner）

```bash
# 2.3.1 在真机上装 NFS 服务端并导出目录（这台机器就是"存储服务器"）
sudo apt install -y nfs-kernel-server
sudo mkdir -p /srv/nfs/k8s && sudo chmod 777 /srv/nfs/k8s
echo '/srv/nfs/k8s *(rw,sync,no_subtree_check,no_root_squash)' | sudo tee -a /etc/exports
sudo exportfs -ra && sudo systemctl enable --now nfs-kernel-server

# 2.3.2 装 provisioner（Helm 官方 chart，注意 --set nfs.server 填服务器 IP）
helm repo add nfs-subdir-external-provisioner https://kubernetes-sigs.github.io/nfs-subdir-external-provisioner/
helm repo update
helm upgrade --install nfs-provisioner nfs-subdir-external-provisioner/nfs-subdir-external-provisioner \
  --set nfs.server=<服务器IP> \
  --set nfs.path=/srv/nfs/k8s \
  --set storageClass.name=nfs-client \
  --set storageClass.defaultClass=true    # 设成默认：以后没写 storageClass 的 PVC 都由它接单

# 2.3.3 验证：应看到 (default) 标记，且 RKE2 默认的 local-path 类不存在（这是 RKE2 和 kind 的差异）
kubectl get storageclass
```

> **provisioner 干了什么**：它常驻集群，一有 PVC 申请就在 NFS 上建一个子目录、生成一个 PV 挂给 Pod。你删 PVC 时它默认归档数据而不是销毁（安全习惯）。

## 3. Harbor —— 正式镜像仓库

### 3.1 概念：为什么不能一直用裸 registry

04/01 章用的 `registry:2` 是个"裸仓库"：能存镜像，仅此而已。生产需要：

1. **账号体系**——谁能推、谁能拉，按项目隔离（裸仓库谁都能推，等于裸奔）
2. **界面**——看仓库列表、镜像 tag、清理垃圾
3. **镜像扫描**——推送时检查高危漏洞
4. **Helm Chart 仓库**——Chart 也能存进去

Harbor 把这些全包了，是自建环境的事实标准（云上有 ACR/ECR 对应物）。

### 3.2 概念：Harbor 装在哪

Harbor 不装进 K8s 集群，而是**独立部署**（docker compose 方式）——仓库是给集群"供货"的基础设施，和集群解耦更稳：集群挂了仓库还在，仓库升级不影响集群。这也是生产的常见姿势。所以先给真机装 docker（和 00 章 WSL2 里装法一样）：

```bash
# 3.2.1 装 docker（真机）
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER   # 重新登录生效
# 配置镜像加速（国内必做）
sudo mkdir -p /etc/docker
sudo tee /etc/docker/daemon.json > /dev/null <<'EOF'
{
  "registry-mirrors": ["https://docker.m.daocloud.io", "https://dockerproxy.com"]
}
EOF
sudo systemctl enable --now docker && sudo systemctl restart docker
```

### 3.3 自签证书（Harbor 必须 HTTPS）

概念：**镜像仓库必须 HTTPS**——容器运行时（docker/containerd）默认拒绝向 HTTP 仓库推拉镜像，除非显式配不安全选项（生产大忌）。所以先给 Harbor 造一张自签证书：

```bash
# 3.3.1 生成自签证书（CN 和 SAN 都指向 Harbor 域名；sslip.io 域名照旧用）
mkdir -p ~/harbor-cert && cd ~/harbor-cert
openssl req -newkey rsa:4096 -nodes -sha256 -keyout ca.key -x509 -days 3650 \
  -subj "/CN=core.harbor.<服务器IP>.sslip.io" -out ca.crt
openssl req -newkey rsa:4096 -nodes -sha256 -keyout server.key \
  -subj "/CN=core.harbor.<服务器IP>.sslip.io" -out server.csr
cat > extfile.cnf <<'EOF'
subjectAltName = DNS:core.harbor.<服务器IP>.sslip.io
EOF
openssl x509 -req -days 3650 -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -extfile extfile.cnf -out server.crt
```

### 3.4 安装 Harbor

```bash
# 3.4.1 下载离线安装包（内含全部镜像，不依赖网络拉取）
cd ~ && wget https://github.com/goharbor/harbor/releases/download/v2.10.0/harbor-offline-installer-v2.10.0.tgz
tar xzf harbor-offline-installer-v2.10.0.tgz && cd harbor

# 3.4.2 复制配置模板并改三处
cp harbor.yml.tmpl harbor.yml
# 用编辑器改 harbor.yml：
#   hostname: core.harbor.<服务器IP>.sslip.io
#   https.port: 443（打开该段注释）—— 但要先停掉可能占 443 的服务（nginx-ingress 用的是 80/443 吗？
#     真机上 Rancher 的 ingress 服务只在 443 上监听？—— 见下方"端口冲突"坑）
#   https.certificate / private_key 指向 3.3.1 生成的 server.crt / server.key
#   harbor_admin_password: k8s123456

# 3.4.3 安装并启动
sudo ./install.sh

# 3.4.4 验证：docker 登录 + 看容器列表
sudo docker ps | grep harbor   # 十来个容器 Running
```

> **端口冲突坑（重要）**：Harbor 默认要占 80/443，而 04 章 Rancher 的 ingress 控制器也想占 80/443。二者都在同一台机器上会打架。**处理办法（选一）**：
> - 改 harbor.yml 的端口：`http.port: 8080`、`https.port: 8443`，然后所有 Harbor 地址带端口（本手册后续命令按带端口写法给）
> - 或者给真机加一块网卡/一个备用 IP 给 Harbor 用
> 本手册统一按 **`core.harbor.<服务器IP>.sslip.io:8443`** 这种带端口写法走，避免踩坑。

### 3.5 让 RKE2 的 containerd 信任 Harbor（本节能省你三天排障）

概念：**RKE2 不用 docker，它内置 containerd**。containerd 不认识 Harbor 的自签证书，会拒绝拉镜像（报 x509 错误）。要让集群信任 Harbor，需要两步——把 CA 证书放到服务器上 + 在 RKE2 配置里登记这个仓库：

```bash
# 3.5.1 把 Harbor 的 CA 证书放到 RKE2 目录
sudo mkdir -p /etc/rancher/rke2
sudo cp ~/harbor-cert/ca.crt /etc/rancher/rke2/harbor-ca.crt

# 3.5.2 登记仓库（auth 是 Harbor 的 admin 账号；生产建议建专用机器人账号）
sudo tee /etc/rancher/rke2/registries.yaml > /dev/null <<'EOF'
configs:
  "core.harbor.<服务器IP>.sslip.io:8443":
    tls:
      ca_file: /etc/rancher/rke2/harbor-ca.crt
    auth:
      username: admin
      password: k8s123456
EOF

# 3.5.3 重启 RKE2 让配置生效（节点会短暂 NotReady，正常）
sudo systemctl restart rke2-server
kubectl get nodes   # 等它回到 Ready
```

> 这一步是自建环境排名前三的坑：集群里所有镜像都要从这里拉，containerd 不信任它 = 所有 Pod 全部 ImagePullBackOff。

## 4. cert-manager —— 证书自动化

### 4.1 概念：证书是干什么的，cert-manager 又干了什么

HTTPS 依赖"证书"证明"我就是这个域名"。证书有两条路：

- **自签**：自己给自己发证，浏览器不认，用户要点"继续前往"——教学够用，生产不行
- **受信 CA**：证书由浏览器内置信任的机构（如 Let's Encrypt）签发，自动绿锁

**cert-manager 是把"申请证书 → 配置到 ingress → 到期前自动续期"这条手工流程全自动化的组件**。配合 Let's Encrypt（免费受信 CA）就是生产标准做法；教学环境没有公网域名，用自签 CA 走通流程，换 Let's Encrypt 只差一个配置。

### 4.2 安装 + 自签 CA 体系

```bash
# 4.2.1 安装
helm repo add jetstack https://charts.jetstack.io
helm repo update
helm upgrade --install cert-manager jetstack/cert-manager -n cert-manager --create-namespace --set installCRDs=true

# 4.2.2 建两级 Issuer：先自签一个"根 CA"，再用它给应用发证书
#   （模拟"受信机构 + 它的证书"结构，教学上能看清签发链）
kubectl apply -f - <<'EOF'
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: selfsigned-ca
spec:
  selfSigned: {}
---
apiVersion: cert-manager.io/v1
kind: ClusterIssuer
metadata:
  name: k8s-demo-ca
spec:
  ca:
    secretName: k8s-demo-ca-secret
EOF
```

> 概念：ClusterIssuer 是"发证机构"的登记表。生产有公网域名时，把 `k8s-demo-ca` 换成 ACME 类型（填个邮箱指向 Let's Encrypt），其余流程一字不改——这就是 cert-manager 的价值。

### 4.3 给一个真实域名发证书（用 04 章的 nginx-demo 练手）

```bash
# 4.3.1 建 Ingress：host 指向 demo 域名，tls 段声明"这个域名要 HTTPS 证书"，
#       注解告诉 cert-manager"用哪个发证机构"（issuer 是根 CA 的"营业部"，这里直接用根 CA）
kubectl apply -f - <<'EOF'
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: nginx-demo-tls
  annotations:
    cert-manager.io/cluster-issuer: selfsigned-ca
spec:
  ingressClassName: nginx
  tls:
    - hosts: [demo.<服务器IP>.sslip.io]
      secretName: demo-tls
  rules:
    - host: demo.<服务器IP>.sslip.io
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: nginx-demo
                port:
                  number: 80
EOF

# 4.3.2 看证书"生产流水线"：Certificate 资源 Ready 即签发成功
kubectl get certificate
# 输出解读：READY=True 表示 cert-manager 走完了 申请→签发→写入 secret 全程

# 4.3.3 验证 HTTPS（curl -k 忽略证书校验，先看 TLS 有没有生效）
curl -k https://demo.<服务器IP>.sslip.io
```

> 浏览器验证时可以把 4.2.2 根 CA 导出来装进电脑信任列表（`kubectl get secret k8s-demo-ca-secret -o jsonpath='{.data.tls\.crt}' | base64 -d`），绿锁就出现了——证书链"根 CA 被信任 → 其签发的证书被信任"就这个原理。

## 5. k8s-demo 全量部署（真机版）

终于到了把 01 章的整套应用搬上真机的时刻。和 01 的差异只有三处：镜像推 Harbor、存储用 NFS、入口走 MetalLB。

### 5.1 构建镜像推 Harbor

```bash
# 5.1.1 装 JDK17 + Maven（真机，构建发生在这里）
sudo apt update && sudo apt install -y openjdk-17-jdk-headless maven

# 5.1.2 拉代码（或从你自己的 GitLab 拉，02 章建的那个）
cd ~ && git clone https://github.com/Marsvvv/k8s-demo.git && cd k8s-demo

# 5.1.3 编译 + 打镜像（tag 直接指向 Harbor，不再用 localhost:5000）
mvn -q -DskipTests package
docker login core.harbor.<服务器IP>.sslip.io:8443 -u admin -p k8s123456
docker build -f docker/Dockerfile.user    -t core.harbor.<服务器IP>.sslip.io:8443/k8s-demo/user-service:latest .
docker build -f docker/Dockerfile.order   -t core.harbor.<服务器IP>.sslip.io:8443/k8s-demo/order-service:latest .
docker build -f docker/Dockerfile.gateway -t core.harbor.<服务器IP>.sslip.io:8443/k8s-demo/gateway:latest

# 5.1.4 推送（Harbor 里先建好项目：UI 登录 → 项目 → 新建项目 → 名称 k8s-demo，公开）
docker push core.harbor.<服务器IP>.sslip.io:8443/k8s-demo/user-service:latest
docker push core.harbor.<服务器IP>.sslip.io:8443/k8s-demo/order-service:latest
docker push core.harbor.<服务器IP>.sslip.io:8443/k8s-demo/gateway:latest
```

> **仓库地址为什么能省略端口**：因为 3.5.2 已经把仓库连端口一起登记进 containerd 的信任列表，镜像 tag 里带端口、配置里带端口，两边一致即可。

### 5.2 Helm 部署（三处参数替换）

```bash
# 5.2.1 安装：镜像仓库前缀换成 Harbor，存储类换成 nfs-client
helm upgrade --install k8s-demo ./k8s/helm/k8s-demo -n k8s-demo --create-namespace \
  --set image.registry=core.harbor.<服务器IP>.sslip.io:8443/k8s-demo \
  --set mysql.storageClass=nfs-client \
  --set rabbitmq.storageClass=nfs-client \
  --set efk.esStorageClass=nfs-client

# 5.2.2 盯启动（首次从 Harbor 拉全部镜像，3~10 分钟）
kubectl -n k8s-demo get pods -w
# 期望：user/order/gateway 各 2/2、mysql-0 1/1、redis 1/1、rabbitmq 1/1、
#       skywalking-oap/ui、elasticsearch-0、kibana、filebeat（每节点 1 个）

# 5.2.3 出问题时老规矩：describe 看 Events、logs 看日志（心法见 03 手册 §8）
```

> **单机内存预警**：全套含 ES/SkyWalking 需要较多内存，8G 机器可能吃紧。扛不住就裁剪：`--set efk.enabled=false --set skywalking.enabled=false --set userService.replicas=1 --set orderService.replicas=1 --set gateway.replicas=1`（ES 和 SkyWalking 是最吃内存的两个，裁掉不影响业务链路）。生产 16G+ 起步。

### 5.3 入口 + 浏览器验证

```bash
# 5.3.1 业务入口服务改 LoadBalancer（MetalLB 会给它分配第二个 IP）
kubectl -n k8s-demo patch svc <ingress控制器服务名> -p '{"spec":{"type":"LoadBalancer"}}'
# 提示：ingress 控制器在哪个命名空间/叫什么名字，用 kubectl get svc -A | grep ingress 找

# 5.3.2 看分配给业务入口的 IP（和 Rancher 的 192.168.1.200 不同，各占一个）
kubectl -n k8s-demo get svc <ingress控制器服务名>
```

## 常见坑速查

| 现象 | 原因/解决 |
|---|---|
| MetalLB 装了但 LB 还是 Pending | 地址池段和局域网不在同一网段，或 1.3.3 的 yaml 没 apply；`kubectl -n metallb-system logs daemonset/speaker` 看报错 |
| 浏览器开 https://rancher... 打不开 | LB IP 不通：地址池段是否和服务器同网段；局域网能否路由到该 IP |
| Harbor 安装报端口被占 | 80/443 被 Rancher 的 ingress 占着；改 harbor.yml 端口为 8080/8443（见 §3.4 坑） |
| `docker push` 报 x509 证书错 | docker 不认自签证书：把 ca.crt 放进 `/etc/docker/certs.d/core.harbor.<IP>.sslip.io:8443/ca.crt` 再重启 docker |
| Pod 全部 ImagePullBackOff | 99% 是 3.5.2 的 registries.yaml 没配或没重启 rke2-server；`kubectl describe pod` 看是 x509 还是认证失败 |
| PVC 一直 Pending | 没设默认 StorageClass：`kubectl get storageclass` 确认 nfs-client 有 (default) |
| NFS 挂载报 permission denied | /srv/nfs/k8s 权限没放 777，或 exports 里没 no_root_squash |
| cert-manager 证书一直 READY=False | `kubectl describe certificate` 看 Events；常见是 ingress 注解 issuer 名字写错 |
| 部署后内存爆、节点 NotReady | 全套组件吃内存，8G 机器按 §5.2 裁剪 efk/skywalking |
