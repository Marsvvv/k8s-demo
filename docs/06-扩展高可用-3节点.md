# 06-扩展高可用-3节点：让"这台机器挂了"不再等于"集群没了"

> 前置：04、05 完成（单机集群 + 全套应用在生产化运行）
> 适用：再准备两台机器（配置和 node1 相同，Ubuntu Server 24.04，4C8G）
> 目标：把单机扩展成 3 节点高可用——控制面 3 副本、etcd 3 副本，任何一台宕机集群照常工作，并亲手做一次故障演练
> 总耗时：约 2 小时
> 执行位置：shell 命令在对应真机上执行（下文用 `node1/node2/node3` 标注）

---

## 0. 概念先行：高可用到底在解决什么、怎么解决

### 0.1 单机集群的"死穴"在哪

回顾 04 章 §0.4 的伏笔：单机 = 控制面 + etcd + 数据面挤在一台机器。这意味着 **node1 一挂，三样全没**：

- etcd（集群的数据库）没了 → 集群"失忆"，什么状态都读不出来
- apiserver（集群的入口）没了 → kubectl、Rancher 全部失联
- 上面的应用 Pod 也没了（数据面也在这台机器上）

高可用的思路就是**每种角色都多备几份，坏一个还有替补**。

### 0.2 为什么偏偏是 3 台（etcd 的奇数定律）

多台控制面之间要"投票做决定"（比如"某节点死了没"），规则是**过半数同意才生效**。算一笔账：

- 2 台：挂 1 台剩 1 台，1/2 不过半 → 集群瘫痪。而且两台各说各话时（网络分区）谁也凑不齐多数票——**偶数会脑裂**
- 3 台：挂 1 台剩 2 台，2/3 过半 → 照常工作
- 5 台、7 台同理，规律就是 **2N+1**：想扛住 N 台宕机，就要 2N+1 台。扛 1 台宕机的最低成本就是 3 台。

### 0.3 VIP 是什么——控制面需要一个"永远在线的地址"

三台机器都有 apiserver，但你的 kubectl 只能配一个地址。如果 kubectl 连 node1 的 6443，node1 挂了怎么办？

解法：造一个**虚拟 IP（VIP）**，它平时"贴"在 node1 上，node1 挂了就自动"漂"到 node2 上。kubectl 永远只连 VIP，底下谁死了它不关心——**这就是控制面的负载均衡/高可用入口**。

```
kubectl / Rancher 客户端 ──► VIP 192.168.1.100:6443 ──► node1 活着 → 转发给 node1
                                              └─────► node1 挂了 → VIP 漂到 node2 → 转发给 node2
```

实现 VIP 漂移的组件叫 **keepalived**（VRRP 协议，路由器级别的成熟技术）。

## 1. 两台新机器准备（node2、node3）

在 node2、node3 上各执行一遍（内容与 04 章 §1 相同，主机名不同）：

```bash
# node2 上：
sudo swapoff -a && sudo sed -i '/swap/s/^/#/' /etc/fstab
sudo hostnamectl set-hostname k8s-node2
sudo timedatectl set-ntp true
sudo ufw disable

# node3 上：同样执行，主机名换 k8s-node3
```

> 另外确认三台机器**局域网互通**（`ping` 对方 IP），并且 node2/node3 能访问 node1 的 9345 端口（这是新节点"报到"用的端口，node1 关了防火墙的话默认就通）。

## 2. 让 node2、node3 加入集群

**先回 node1 取"扩群钥匙"**——04 章 §2 埋的伏笔在这里兑现：

```bash
# node1 上执行：拿到 node-token（"入群令牌"）
sudo cat /var/lib/rancher/rke2/server/node-token
```

然后在 **node2 和 node3** 上各执行：

```bash
# 2.1 安装（和 04 一样）
curl -sfL https://get.rke2.io | sudo sh -

# 2.2 写入"入群配置"：server 指向 node1 的注册端口 9345，token 用刚取的那串
#    <node1的IP> 换成实际 IP，<token> 换成上面 cat 出来的内容
sudo mkdir -p /etc/rancher/rke2
sudo tee /etc/rancher/rke2/config.yaml > /dev/null <<'EOF'
server: https://<node1的IP>:9345
token: <token>
EOF

# 2.3 启动（注意：新机器也起 rke2-server，不是 agent——它们将成为控制面成员）
sudo systemctl enable --now rke2-server

# 2.4 盯日志，看到 kubelet 相关日志即完成
sudo journalctl -u rke2-server -f
```

**回 node1 验证扩群结果**：

```bash
kubectl get nodes -o wide
# 输出解读：现在应看到 3 个节点，ROLES 都是 control-plane,etcd,master 三合一
#   —— 这就是"3 控制面 + 3 etcd"的高可用形态
#   STATUS 全 Ready、AGE 从 0 开始增长 = 新节点已入群
```

> **一个容易误解的点**：新节点的 kubeconfig 不需要配——控制面节点之间通过 9345 注册、通过 etcd 同步状态，你只需要从 node1 用 kubectl 看它们。想在任何一台机器上都能 kubectl 的话，把 node1 的 ~/.kube/config 拷过去即可（下一步就要这么干）。

## 3. 浮动 VIP：三台机器装上 keepalived

### 3.1 概念回顾

keepalived 在三台机器上各自运行、互相用 VRRP 协议"开会"：优先级高的持有 VIP。node1 失联超过约定时间，node2（次高优先级）就把 VIP 接过来。对客户端来说 VIP 从未掉线。

### 3.2 安装与配置（三台都装）

```bash
# 三台机器都执行：
sudo apt install -y keepalived
```

然后**每台写一份配置**，差别只在 priority（100/90/80）和主机名：

```bash
# node1 上执行（MASTER，优先级 100）：
sudo tee /etc/keepalived/keepalived.conf > /dev/null <<'EOF'
vrrp_instance K8S_VIP {
    state MASTER
    interface eth0            # 改成你的网卡名（ip a 看哪个是局域网口）
    virtual_router_id 51      # 三台必须一致，这是"我们是一组"的组号
    priority 100
    advert_int 1
    authentication {
        auth_type PASS
        auth_pass k8s123456
    }
    virtual_ipaddress {
        192.168.1.100/24      # VIP：局域网里一个空闲 IP，三台配置一致
    }
}
EOF
sudo systemctl enable --now keepalived

# node2 上：同内容，但 state BACKUP、priority 90
# node3 上：同内容，但 state BACKUP、priority 80
```

### 3.3 验证 VIP 生效

```bash
# node1 上：VIP 应出现在网卡上
ip addr show eth0 | grep 192.168.1.100

# 现在把 kubectl 的"入口地址"换成 VIP——先在 node1 上改自己的 kubeconfig：
sed -i 's#https://<node1的IP>:6443#https://192.168.1.100:6443#' ~/.kube/config
kubectl get nodes   # 走 VIP 访问，照常输出 = VIP 转发生效
```

> 顺手把 kubeconfig 拷给 node2/node3（`scp` 或手动复制），这样三台机器都能 `kubectl`，而且全部走 VIP——为下面的演练做好准备。

## 4. 故障演练：亲手"杀死"node1（本章高潮）

这是全项目最重要的一次实验——**先验证"高可用"不是嘴上说说**：

```bash
# 4.1 在 node1 上执行：停掉整个 RKE2（模拟宕机；用 systemctl stop 而不是 shutdown，方便演练后自己恢复）
sudo systemctl stop rke2-server

# 4.2 立即到 node2 上观察三件事：
#   ① VIP 漂移：node2 的网卡上出现了 192.168.1.100（优先级次高的接盘）
ip addr show eth0 | grep 192.168.1.100
#   ② 集群仍然可操作：kubectl 走 VIP，照常输出
kubectl get nodes
# 输出解读：node1 显示 NotReady（它挂了），但 node2/node3 Ready，集群可用！
#   ③ 应用是否受影响：k8s-demo 的 Pod 会自动迁移到活着的节点（数据在 NFS 上，跟着走）
kubectl -n k8s-demo get pods -o wide
# 浏览器再下几单验证业务不受影响（入口 LB IP 由 MetalLB 自动漂移，也是活的）

# 4.3 恢复：node1 上把服务拉起来，等它重新入群
sudo systemctl start rke2-server
kubectl get nodes   # node1 从 NotReady 回到 Ready，一切如初
```

> **演练后的认知盘点**：
> - 控制面高可用（3 台）+ VIP 漂移 → kubectl/Rancher 不断线
> - etcd 3 副本 → 挂 1 台仍有 2/3 多数票
> - 应用高可用：Pod 会自动迁到活节点，NFS 让数据跟着 Pod 走（05 章 §2 的伏笔在这里兑现）
> - MetalLB 的 speaker 每个节点都有，业务入口 IP 也自动漂移（05 章 §1 的伏笔）
>
> 这一连串"自动"，就是 K8s 平台层的价值：**你只写了"要 2 个副本"，平台替你扛住了一台机器宕机**。

## 5. worker 节点：给集群加"只干活的机器"

### 5.1 概念：什么时候需要 worker

现在三台机器都是"又当领导又干活"（控制面+数据面合一）。当应用多了、控制面资源吃紧，或生产上希望控制面"专职管理"时，就加纯 worker 节点——只跑应用 Pod，不参与控制面投票。

### 5.2 加一台 worker（第四台机器，可选练习）

```bash
# 第四台机器（node4）上执行：
curl -sfL https://get.rke2.io | sudo sh -
sudo mkdir -p /etc/rancher/rke2
sudo tee /etc/rancher/rke2/config.yaml > /dev/null <<'EOF'
server: https://192.168.1.100:9345   # 用 VIP！这样任何一台控制面挂都不影响新节点入群
token: <token>
EOF
# 关键差异：起 rke2-agent 而不是 rke2-server
sudo systemctl enable --now rke2-agent

# 验证：node1 上看
kubectl get nodes
# 输出解读：node4 的 ROLES 是 <none> —— 它不参与控制面投票，只跑应用
```

> 生产经验：控制面 3 台"只做管理"（可以打污点禁止调度应用），worker 若干台跑业务。你们真实项目按业务量定 worker 数量即可。

## 6. 剩下的单点盘点（诚实的收尾）

高可用是"木桶原理"，3 节点解决了集群层，但盘点一下其他单点，做到心里有数：

| 组件 | 现状 | 单点风险 | 生产建议 |
|---|---|---|---|
| K8s 控制面/etcd | 3 副本 ✅ | 已解决 | 已达标 |
| 业务入口（MetalLB） | L2 模式，IP 自动漂移 ✅ | 已解决 | BGP 模式更稳 |
| Rancher 管理面 | 单副本 ⚠️ | Rancher 挂了不能"用界面管"，但集群/应用不受影响（04 章验证过） | `helm upgrade rancher ... --set replicas=3` + 外部 MySQL |
| Harbor 仓库 | 单机 ⚠️ | 仓库挂了不能发版，但已部署的应用不受影响 | 生产上镜像仓库独立高可用或云 ACR |
| NFS 存储 | 单机 ⚠️ | 存储机挂了，依赖 PVC 的应用全受影响（这是最危险的单点） | 生产用 Ceph/云盘等分布式存储 |
| 交换机/路由器/机房 | 物理单点 ⚠️ | 一切网络的前提 | 数据中心级别的事，知道即可 |

> 认知结论：**高可用是有成本的逐层叠加**。教学环境到"3 节点 + 应用多副本"就是很好的状态；生产环境按上表逐项补齐，每一项都要真金白银（机器、人力、复杂度）。

## 常见坑速查

| 现象 | 原因/解决 |
|---|---|
| node2 加入后一直 NotReady | `journalctl -u rke2-server -f` 看：token 不对、9345 不通（node1 防火墙）、时间不同步（证书报错）最常见 |
| VIP 不漂移 | 三台 keepalived 的 virtual_router_id 不一致，或组播被网络设备屏蔽；`journalctl -u keepalived` 看状态 |
| VIP 配好但 kubectl 连不上 | kubeconfig 的 server 地址还是旧 IP（§3.3 的 sed 没生效）；或 6443 没被 VIP 转发（确认 keepalived 在跑） |
| 停 node1 后 etcd 报错 | 正常现象：3 台停 1 台仍在多数票内；但**再停 1 台集群就真的瘫了**（1/3 不过半），演练别过度 |
| 新节点拉镜像失败 | 05 章的 registries.yaml 只在 node1 配过——**每台新机器都要重新配** /etc/rancher/rke2/registries.yaml + 拷贝 CA |
| NFS 挂载失败（应用迁到新节点后） | 新节点没装 nfs-common（挂载客户端）；`sudo apt install -y nfs-common` |
| 应用 Pod 长时间 Terminating | Pod 迁走时旧节点已失联，K8s 要等宽限期；正常，耐心等或强制删 |
