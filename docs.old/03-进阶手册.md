## 1. Helm 化发布（把 raw YAML 升级为包管理）

项目里已备好完整 chart（`k8s/helm/k8s-demo`），与 raw/ 等价、参数化：

```bash
cd ~/k8s-demo

# 1.1 卸载 raw 方式部署的部分资源（避免同名冲突）——保留 namespace
kubectl delete -f k8s/raw/ --ignore-not-found=true
kubectl delete pvc -n k8s-demo --all

# 1.2 Helm 一键安装全套
helm upgrade --install k8s-demo ./k8s/helm/k8s-demo -n k8s-demo --create-namespace

# 1.3 常用操作
helm list -n k8s-demo                       # 看已装 release
helm get values k8s-demo -n k8s-demo        # 看当前参数
helm upgrade --install k8s-demo ./k8s/helm/k8s-demo -n k8s-demo \
  --set image.tag=v2 --set userService.replicas=3    # 改参数发布
helm rollback k8s-demo -n k8s-demo          # 回滚到上一版本
helm uninstall k8s-demo -n k8s-demo         # 卸载
```

> 真实线上一句话：**手写 YAML 是理解原理，Helm 是工程化交付**。CI 的 deploy 阶段也可以换成 `helm upgrade --set image.tag=$CI_COMMIT_SHORT_SHA`（作业：把 .gitlab-ci.yml 的 deploy 段改成 Helm 发布）。

## 4. NetworkPolicy（需要换 Calico CNI）

kind 默认 kindnet 不支持 NetworkPolicy，重建集群装 Calico：

```bash
# 4.1 重建集群（禁用默认 CNI）
kind delete cluster
cat <<EOF | kind create cluster --config=-
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
networking:
  disableDefaultCNI: true
EOF
# 重建 registry 连接（重新跑 docs/kind/kind-with-registry.sh 或手动 docker network connect kind kind-registry）

# 4.2 装 Calico
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.27.0/manifests/calico.yaml
kubectl wait --namespace kube-system --for=condition=ready pod -l k8s-app=calico-node --timeout=180s

# 4.3 重新部署应用 + 应用网络策略
kubectl apply -f k8s/raw/
# 验证隔离：现在从 order-service Pod 里 curl mysql 应该不通了（策略里只允许 user→mysql）
kubectl -n k8s-demo exec deployment/order-service -- wget -qO- --timeout=2 http://mysql:3306 || echo "已隔离 ✓"
```

> 网络策略文件在 `k8s/raw/10-networkpolicy.yaml`，流矩阵注释里画得清楚。

## 6. Prometheus + Grafana 监控

```bash
# 6.1 安装（Helm，注意国内网络，卡住多试几次）
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm upgrade --install kube-prometheus-stack prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace \
  --set prometheus.resources.requests.memory=1Gi \
  --set grafana.adminPassword=k8s123456

# 6.2 访问 Grafana（默认 ClusterIP，先端口转发）
kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80

```

### 7.1 日志检索 EFK（已内置：k8s/raw/12~14，01 手册已部署）

部署后 `http://kibana.local` 即可用。几个值得做的练习：

1. **看采集链路**：`kubectl -n k8s-demo get daemonset filebeat`——3 个节点各 1 个采集器（DaemonSet 的本质）
2. **按服务筛选日志**：Discover 页筛选 `kubernetes.labels.app: "order-service"`，只看订单服务
3. **全文检索**：搜"缓存命中"或"收到下单消息"，验证 Redis/MQ 的日志证据在集中平台也能查到
4. **观察滚动更新日志**：改代码 CI 发版时，Kibana 里能同时看到新旧 Pod 的日志交替（上线过程全景）

> 本项目代码已按 12-factor 把日志打到 stdout（`kubectl logs` 看到的就是采集源），
> Filebeat 零侵入收走——这就是"日志采集不改业务代码"的含义。

**对比方案（Phase 5 可选体验）**：

| 方案 | 组成 | 特点 |
|---|---|---|
| EFK（本项目已内置） | Filebeat → ES → Kibana | 国内自建主流；全文检索/聚合最强；ES 吃内存 |
| PLG（云原生轻量） | Promtail → Loki → Grafana | 按标签索引（不做全文），几百 MB 内存够用；与 §6 的 Grafana 一体化 |

> 生产注意：本项目 ES 为教学简化（单节点、无认证、关 ILM）；真实线上是 3 节点集群 + xpack 认证 + 索引生命周期 + 定期清理磁盘。

## 8. 全局故障排查心法（背下来）

```
1. kubectl get pods -n k8s-demo -o wide     # 谁没 Ready、在哪个节点
2. kubectl describe pod <pod> -n k8s-demo   # Events 是 90% 问题的答案
3. kubectl logs <pod> -n k8s-demo --previous  # 上次崩的原因
4. kubectl exec -it <pod> -n k8s-demo -- sh   # 进容器看现场
5. kubectl get events -n k8s-demo --sort-by=.lastTimestamp | tail   # 全局事件
```
